# Memory — Real LinkedIn OAuth connect flow + local AI/demo fixes

Last updated: 2026-09-11

## What was built

- **Platform-form UI fixes**: fixed the "Add platform" dialog's Fill-test-data/close-button overlap (`PlatformFormDialog.tsx`). Added a Logo field — after trying the company `@ascentware/react-ui-library`'s `FileUploadField` (found and worked around a real bug: its image-vs-file preview detection fails on plain `data:` URLs, since its regex needs a literal file extension in the string — fixed upstream-side by appending a harmless `#/name.png` URL fragment), it was reverted back to a small custom `components/ui/LogoUpload.tsx` per explicit user direction: the library's component is a full-width dropzone with no compact variant, which didn't fit next to the Name field.
- **Post History**: added a "Post now" send-icon action shown only on draft-status rows (`PostHistoryTable.tsx`), wired to `submitPost` — which was extended (`lib/posts/store.tsx`) to also publish `"draft"`-status drafts, not just freshly-generated `"ready"` ones.
- **Local AI generation, no paid key needed**: `apps/api/src/ai/ai.service.ts` now auto-falls-back when `OPENAI_API_KEY` isn't set — real free image generation via Pollinations.ai (works reliably, no key), and **local template-based** caption/hashtag/rewrite generation (not a real free LLM — Pollinations' text API turned out to require a funded key for any non-cached prompt and rate-limits anonymous callers to 1 concurrent request, so it was dropped in favor of simple deterministic templates). Both paths automatically prefer real OpenAI the moment a key is set — no config changes needed later.
- **Real "Connect with LinkedIn" OAuth 2.0 flow — the main piece of this session.** New `apps/api/src/platforms/oauth/linkedin-oauth.service.ts` + `linkedin-oauth.controller.ts` (registered in `platforms.module.ts`):
  - `GET /platforms/:id/oauth/linkedin/start` — reads the platform's own Client ID credential field (decrypting if marked secret), redirects to LinkedIn's real consent screen.
  - `GET /platforms/oauth/linkedin/callback` — **fixed path** (no platform id in it — that's what must be registered as the "Authorized redirect URL" in LinkedIn's Developer Portal, since LinkedIn requires an exact string match and the id shouldn't need to be re-registered per environment). Exchanges the code for an access token, resolves an author URN (org first if scope allows, else the member's own profile via `/v2/userinfo`), saves both into the platform's `access-token`/`organization-urn` `CredentialField` rows (upsert, encrypted).
  - In-memory CSRF `state` store (10-min TTL) — fine for this single-instance demo backend.
  - Frontend: "Connect with LinkedIn" button in `PlatformFormDialog.tsx` (shown only when editing the LinkedIn platform), a real top-level `window.location.href` redirect (not a route push — has to leave the SPA). `PlatformsView.tsx` detects the `?linkedin=connected|error` return, shows a dismissible status banner (decodes LinkedIn's HTML-entity-encoded error text, e.g. literal `&quot;`), calls `refetch()` (newly exposed from `usePlatforms()` — wasn't in the context value before), and auto-reopens the LinkedIn edit dialog once (ref-guarded) so the filled-in fields are visible immediately.
- **Personal-profile pivot**: the user's real LinkedIn Developer App only has the default scopes approved (`openid`, `profile`, `w_member_social`, `email`) — not `w_organization_social`/`r_organization_social`/`rw_organization_admin`, which need LinkedIn's "Community Management API" product (external review). First real OAuth attempt hit LinkedIn's own "scope not authorized" error. User chose to post from their **own personal profile** instead of a company page for now, so the flow was updated: requested scopes are now `openid profile w_member_social`; added `lookupPersonUrn()` (via `/v2/userinfo`'s `sub` claim → `urn:li:person:{sub}`); `lookupAuthorUrn()` tries the organization lookup first (harmless no-op without org scope) then falls back to the person URN. `linkedin.connector.ts`'s Connect-validation step now branches on URN prefix (`urn:li:person:` vs `urn:li:organization:`) to call the right LinkedIn lookup. **`linkedin.provider.ts` (the actual publish code) needed zero changes** — it already treats the stored URN as an opaque `author`/`owner` value, and LinkedIn's Posts/image-upload APIs accept either URN type interchangeably in that field.

## Decisions made

- **Credential field key stays `organization-urn`** even though it may now hold a `urn:li:person:...` value — renaming it would touch the connector, provider, and existing DB rows for no functional benefit; a code comment documents the dual purpose instead.
- **OAuth scopes are requested to match exactly what the app has approved**, not what would be ideal — requesting an unapproved scope makes LinkedIn's own authorize endpoint reject the request before reaching the consent screen at all (confirmed both failure modes: a generic "Bummer" error page, and a proper `error=...&error_description=...` redirect carrying a scope-authorization message).
- **Demo runs locally** (`apps/api` on :4000, `apps/web` on :3000), not on the live Vercel deployment — deliberate, made before this session's LinkedIn work started, because the production `apps/web` had `NEXT_PUBLIC_API_URL` misconfigured to `localhost:8080` and the deployed `apps/api` sits behind Vercel's SSO Deployment Protection (`all_except_custom_domains`), both unresolved (see Open questions).
- **Client ID/Secret live on the Platform's own CredentialFields**, not app-wide env vars — keeps the OAuth flow generic to whatever Platform row is named "LinkedIn", consistent with how the rest of this app's credential model already works.

## Problems solved

- **Pollinations.ai's free text/chat API is not actually usable for a live demo**: looks free on paper, but requires a funded key for any prompt that isn't already cache-hit, and separately rate-limits anonymous callers to 1 concurrent request. Image generation on the same provider works fine and free. Solved by keeping Pollinations for images only and switching text generation to local templates.
- **A real bug in `@ascentware/react-ui-library`'s `FileUploadField`**: its inline preview can't detect a plain base64 `data:` URL as an image (regex needs a literal file extension), so it rendered a broken-looking generic-document icon instead of a thumbnail. Worked around (when that component was still in use) by appending `#/filename.ext` to the data URL — browsers strip URL fragments before decoding an `<img src>`, but the string still contains the extension the library's regex needs.
- **`client-id` was found to also be marked `secret: true`** in the user's stored data (not just `client-secret`) — an early version of the OAuth service only decrypted `client-secret`, which would have silently sent a ciphertext string as the real Client ID. Fixed via a shared `fieldValue()` helper that always checks the `secret` flag before using a field's value.
- **User had misconfigured the LinkedIn platform's credential fields** before this session's OAuth work: instead of the two fields the backend actually reads (`Access Token`, `Organization URN`), they'd entered a full OAuth-app credential set (Client ID, Client Secret, redirect URL, post api, Authorization URL, Token URL) — those don't do anything on their own since this app has no OAuth exchange logic to use them... until this session built exactly that, which is what let those already-entered Client ID/Secret values become useful instead of being replaced.
- **LinkedIn's OAuth error text arrives HTML-entity-encoded** (e.g. literal `&quot;`) — fixed by decoding common entities before displaying the status banner.
